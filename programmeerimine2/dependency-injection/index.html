Dependency Injection¶

Dependency Injection (DI) ehk sõltuvuse injekteerimine on viis, kuidas objekt saab endale vajalikud teised objektid kätte mitte ise luues, vaid väljastpoolt vastu võttes. See on ASP.NET Core rakenduste alustala – konteiner, mis teenuseid loob ja jagab, on raamistikku sisse ehitatud.

Selles materjalis vaatame, mis on sõltuvus, miks tihe sidumine on probleem, kuidas DI töötab ning kuidas seda .NET-is kasutada.

Mis on sõltuvus?¶

Klass on sõltuvuses teisest klassist, kui ta vajab oma tööks selle objekti. Kui BookService kasutab LibraryDbContext-i, siis on BookService sõltuvuses LibraryDbContext-ist.

Probleem tekib siis, kui klass loob selle sõltuvuse ise:

public class BookService
{
    private readonly LibraryDbContext _dbContext = new LibraryDbContext();

    public List<Book> GetAll()
    {
        return _dbContext.Books.ToList();
    }
}

Selline kood on tihedalt seotud (ingl tight coupling):

  • BookService teab täpselt, milline andmebaasi klass tal on
  • Andmebaasi asemel ei saa kasutada näiteks fiktiivset andmeallikat
  • Kui tahame vahetada LibraryDbContext näiteks teise implementatsiooni vastu, peame muutma BookService koodi

Lahendus: sõltuvuse injekteerimine¶

DI põhireegel on lihtne:

Dependency Injection põhireegel

Klass ei loo oma sõltuvusi ise, vaid võtab need konstruktori kaudu vastu.

public class BookService
{
    private readonly LibraryDbContext _dbContext;

    // Sõltuvus tuleb seestpoolt, mitte ei looda ise
    public BookService(LibraryDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    public List<Book> GetAll()
    {
        return _dbContext.Books.ToList();
    }
}

Nüüd otsustab keegi teine, millise objekti BookService-ile kätte annab. Tavaliselt on seeks ASP.NET Core-i teenuste konteiner.

Kuidas näeb välja loomine ilma DI-ta?¶

// Iga koht, kus teenust vaja on, peab teadma, kuidas see kokku panna
var dbContext = new LibraryDbContext(options);
var repository = new BookRepository(dbContext);
var service = new BookService(repository);

Kuidas näeb välja loomine DI-ga?¶

// Konteiner teab ise, mida ja millesse panna
var service = sp.GetRequiredService<BookService>();

Teenuste registreerimine .NET-is¶

ASP.NET Core rakenduses registreeritakse teenused Program.cs-is. Sealsest builder.Services-ist saabki konteiner:

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddDbContext<LibraryDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("DefaultConnection")));

// Registreeri oma teenused
builder.Services.AddScoped<IBookRepository, SqlBookRepository>();
builder.Services.AddScoped<BookService>();

var app = builder.Build();

Registreerimise ajal me veel ei loo objekte – kirjutame ainult alla, mis on olemas. Objektid luuakse siis, kui keegi neid esimest korda küsib.

Teenuste eluajad (lifetimes)¶

Iga registreeritud teenuse puhul tuleb valida, kaua tema objekt elab:

Eluaeg Registreerimine Objekti eluiga Näide
Transient AddTransient<T>() Iga pöördumise/küsimise kohta uus objekt Kerge, olemitu teenus, näiteks päringu logija
Scoped AddScoped<T>() Ühe HTTP päringu jooksul sama objekt, uus päring = uus objekt DbContext, repository
Singleton AddSingleton<T>() Kogu rakenduse eluea jooksul üks objekt Puhver, konfiguratsiooni jälgija, statmeetika

Ettevaatust!

  • DbContext on scoped – kunagi ära registreeri teda Singleton-ina, muidu jagavad kõik päringud sama konteksti ja tekivad keerulised vead
  • Singleton teenuses ei tohi hoida scoped teenust (nt DbContext)

Interfeiss ja implementatsioon¶

DI kõige kasulikum osa on see, et saame registreerida interfeisi ja selle taga peituvat klassi vahetada ilma kuskil muud muutmata:

public interface IBookRepository
{
    Task<List<Book>> GetAllAsync();
    Task AddAsync(Book book);
}

public class SqlBookRepository : IBookRepository
{
    private readonly LibraryDbContext _dbContext;

    public SqlBookRepository(LibraryDbContext dbContext)
    {
        _dbContext = dbContext;
    }

    public async Task<List<Book>> GetAllAsync()
    {
        return await _dbContext.Books.ToListAsync();
    }

    public async Task AddAsync(Book book)
    {
        _dbContext.Books.Add(book);
        await _dbContext.SaveChangesAsync();
    }
}

// Program.cs
builder.Services.AddScoped<IBookRepository, SqlBookRepository>();
builder.Services.AddScoped<BookService>();

BookService küsib konstruktorist IBookRepository ja ei tea midagi sellest, kas taga on SQL-i andmebaas või mõni muu andmeallikas:

public class BookService
{
    private readonly IBookRepository _repository;

    public BookService(IBookRepository repository)
    {
        _repository = repository;
    }

    public Task<List<Book>> GetBooksAsync() => _repository.GetAllAsync();
    public Task AddBookAsync(Book book) => _repository.AddAsync(book);
}

Miks interfeiss?

Interfeissi kaudu saame vahetada implementatsiooni (nt SqlBookRepository → InMemoryBookRepository) muutmata ühtegi tarbija koodi.

Teenuse saamine kätte¶

1. Konstruktori injekteerimine (kõige levinum)¶

Teenuse küsimine konstruktori parameetri kaudu. Nii teevad kontrollerid, handlerid ja kõik muud teenused:

[ApiController]
[Route("api/[controller]")]
public class BooksController : ControllerBase
{
    private readonly BookService _bookService;

    public BooksController(BookService bookService)
    {
        _bookService = bookService;
    }

    [HttpGet]
    public async Task<IActionResult> GetAll()
    {
        var books = await _bookService.GetBooksAsync();
        return Ok(books);
    }
}

Kontrollerit ei loo me ise – ASP.NET Core loob iga päringu jaoks uue kontrolleri ja paneb sinna kohaliku scoped teenused.

2. Meetodi injekteerimine¶

Vahel on vaja teenust ainult ühes meetodis – siis võib selle võtta meetodi parameetrisse:

public IActionResult Get([FromServices] IBookRepository repository)
{
    return Ok(repository.GetAllAsync());
}

3. IServiceProvider (harv kasutus)¶

var service = httpContext.RequestServices.GetRequiredService<IBookRepository>();

Anti-muster

Kui hakkad GetRequiredService-i igal pool kasutama, muutub kood teenuse lokalisaatori mustriks, mis on DI vastand. Eelista alati konstruktori injekteerimist.

Näide: terviklik Web API lõik¶

Kontroller → teenus → repository → andmebaas, kõik DI kaudu:

// Program.cs
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddDbContext<LibraryDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("DefaultConnection")));

builder.Services.AddScoped<IBookRepository, SqlBookRepository>();
builder.Services.AddScoped<IBookService, BookService>();

var app = builder.Build();

app.MapControllers();
app.Run();

// BooksController.cs
public class BooksController : ControllerBase
{
    private readonly IBookService _bookService;

    public BooksController(IBookService bookService)
    {
        _bookService = bookService;
    }

    [HttpPost]
    public async Task<IActionResult> Create([FromBody] SaveBookCommand command)
    {
        await _bookService.SaveAsync(command);
        return StatusCode(StatusCodes.Status201Created);
    }
}

Teenuse ja repository vahel võib vabalt olla CQRS-i handler – ka tema saab oma sõltuvused konstruktori kaudu:

public class SaveBookCommandHandler
{
    private readonly IBookRepository _repository;

    public SaveBookCommandHandler(IBookRepository repository)
    {
        _repository = repository;
    }

    public async Task Handle(SaveBookCommand command)
    {
        var book = new Book { Title = command.Title, Author = command.Author };
        await _repository.AddAsync(book);
    }
}

Registreerimise korraldamine¶

Kui teenuseid kuhjub, ei jääda Program.cs-i kõike topima – registreerimise viiakse eraldi laiendusmeetoditesse:

public static class ServiceCollectionExtensions
{
    public static IServiceCollection AddApplicationServices(this IServiceCollection services)
    {
        services.AddScoped<IBookRepository, SqlBookRepository>();
        services.AddScoped<IBookService, BookService>();
        services.AddScoped<SaveBookCommandHandler>();
        return services;
    }
}

// Program.cs jääb puhtaks
builder.Services.AddApplicationServices();

Kolmanda osapoole konteinerid¶

ASP.NET Core-i sisseehitatud konteiner (Microsoft.Extensions.DependencyInjection) on enamiku rakenduste jaoks küllalt. Suurtes projektides kasutatakse vahel ka tugevamaid lahendusi:

Konteiner Lisavõimalused
Microsoft.Extensions.DependencyInjection Kaasas ASP.NET Core-iga, kiire, lihtne
Autofac Automoodulid, eluaja valikud, keerukamad konfiguratsioonid
DryIoc Väga kiire, CompactModeli tugi
Scrutor Registreerimine konventsiooni järgi (nt "lisa kõik I*Service klassid")

Konteineri vahetamine on lihtne, sest rakendus loeb teenuseid üldjuhul ainult IServiceCollection ja IServiceProvider kaudu.

Kokkuvõte¶

  • Sõltuvus – klass vajab teist klassi oma tööks
  • DI – sõltuvused tulevad konstruktori kaudu väljastpoolt, mitte ei sünni klassis
  • Konteiner (builder.Services) teab, mis on registreeritud ja loob objektid vajadusel
  • Transient – uus objekt iga kord, Scoped – ühe päringu jooksul, Singleton – kogu rakenduse elu
  • Interfeiss + implementatsioon muudab koodi vahetatavaks
  • Eelista konstruktori injekteerimist, mitte GetRequiredService-i kutset kõikjal

Harjutused¶

  1. Loo ASP.NET Core Web API, kus on interfeiss IEmailService ja klass SmtpEmailService. Registreeri teenus Program.cs-is ja injekteeri see kontrollerisse, mille POST päring "saadab" e-kirja (prindib selle konsolile).
  2. Lisa eelmisele ülesandele teine implementatsioon ConsoleEmailService, mis kirjutab kirja asemel faili. Vaheta ainult üks rida Program.cs-is – veendu, et kontrolleri kood ei muutunud.
  3. Loo teenus IRandomService meetodiga int Next(int min, int max). Registreeri see singletonina ja transiendina eraldi projektides. Vaata dotnet watch abil, kas tulemused korduvad või mitte, ja selgita, miks.
  4. Refaktoreeri olemasolevasse Web API projekti repository muster: loo IBookRepository, vii andmebaasipäringud BookService-ist repository-sse ja korralda registreerimine eraldi ServiceCollectionExtensions klassis.
  5. (Raske) Uuri oma viimase projektiga builder.Services-i ja kirjuta üles, millised teenused on scoped, millised singletonid. Kontrolli, kas mõni singleton ei hoida juhuslikult scoped teenust.
