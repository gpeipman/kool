Failide kasutamine¶

Paljud rakendused peavad lisaks andmebaasiandmetele hoidma ka faile: lepinguid PDF-idena, arveid, kasutajate pilte või manuseid. Failide hoidmiseks on mitu võimalust – kohalik ketas, võrguketas, Azure Blob Storage, Amazon S3. Iga hoidla kasutamise viis on erinev, seetõttu tekib kiusatus kirjutada failide lugemine ja salvestamine otse sinna, kus parasjagu vaja on.

Selles peatükis vaatame, miks selline lähenemine pikemas perspektiivis halb on, kuidas peita failihoidla IFileClient liidese taha, kuidas faili ASP.NET Core Web API-s vastu võtta ning kuidas kirjutada CQRS-i command, mis faili ära salvestab.

Probleem: failikood hajub mööda rakendust¶

Kõige lihtsam viis fail salvestada on kirjutada see otse kontrolleris kettale:

[HttpPost("{id}/file")]
public async Task<IActionResult> UploadFile(int id, IFormFile file)
{
    var path = Path.Combine("C:\\uploads\\contracts", id + ".pdf");

    await using var stream = System.IO.File.Create(path);
    await file.CopyToAsync(stream);

    return Ok();
}

See kood töötab ühe masina peal. Päris rakenduses tekib aga hulk probleeme:

  • Asukoht on koodi sisse kirjutatud. Arendusmasinas on üks tee, serveris teine, konteineris kolmas. Iga keskkonna jaoks tuleb koodi muuta.
  • Sama kood kordub. Iga uus failitüüp (arved, pildid, manused) toob kaasa veel ühe sarnase meetodi, kus on oma tee, oma kontrollid ja oma veakäsitlus.
  • Testimine puudutab päris ketast. Test käivitub arendaja masinal ja kirjutab faile, mida hiljem keegi ei korista.
  • Hoidla vahetamine on kallis. Kui tahame minna Azure Blob Storage'i või Amazon S3 peale, tuleb muuta iga kohta, kus failidega töötatakse.
  • Pilvekeskkonnas ei püsi failid kettal. Azure App Service'i või konteineri kohalik ketas on ajutine – uue instantsi käivitumisel kaob sealt kõik.
  • Turvalisus jääb igaühe hooleks. Kliendi antud failinimi võib sisaldada kaustateed (..\..\appsettings.json) või katta olemasoleva faili.
  • Kontroller teab liiga palju. Kontroller peaks tegelema HTTP-päringu vastuvõtmisega, mitte sellega, kus ja kuidas fail kettale läheb.

Tähelepanu: File tähendus kontrolleris

Kontrolleris varjab ControllerBase.File() meetod System.IO.File klassi. Seepärast tuleb kontrolleris kirjutada System.IO.File.WriteAllBytesAsync(...), mitte lihtsalt File.WriteAllBytesAsync(...). See on veel üks märk sellest, et failioperatsioonid ei kuulu kontrollerisse.

Probleemi juur on tihe side (ingl tight coupling) failisüsteemiga. Lahendus on sama, mida kasutasime andmebaasi puhul: peidame tehnilise detaili liidese taha ja laseme sõltuvusel tulla väljastpoolt.

IFileClient liides¶

IFileClient kirjeldab kõik failioperatsioonid, mida rakendus vajab. Liides ei tea, kus failid tegelikult asuvad ega kuidas need kettale kirjutatakse.

public interface IFileClient
{
    Task SaveFileAsync(string storeName, string fileName, byte[] content);
    Task<byte[]> GetFileAsync(string storeName, string fileName);
    Task<bool> FileExistsAsync(string storeName, string fileName);
    Task DeleteFileAsync(string storeName, string fileName);
    string GetFileUrl(string storeName, string fileName);
}
Meetod Mida teeb
SaveFileAsync Salvestab faili sisu hoidlasse storeName. Kui sama nimega fail on olemas, kirjutatakse see üle.
GetFileAsync Tagastab faili sisu baitidena või null, kui faili ei ole.
FileExistsAsync Kontrollib, kas fail on hoidlas olemas.
DeleteFileAsync Kustutab faili.
GetFileUrl Tagastab faili URL-i. Kohaliku ketta puhul on see staatiline URL, blob-hoidla puhul avalik link.

Meetodid on async, sest ketta- ja võrgupöördumised on aeglased. Kui kontroller või handler ootab await-iga, ei blokeeri ta selle ajal teisi päringuid.

Miks byte[] ja mitte Stream?

Väikeste failide (lepingud, arved, pildid) puhul on byte[] kõige lihtsam: faili sisu on üks objekt, mida saab commandiga edasi anda ja testides hõlpsasti asendada. Suurte failide puhul oleks mõistlikum kasutada Stream-i, et kogu faili korraga mällu ei loetaks. Selles kursuses jääme lihtsuse huvides byte[] juurde.

Hoidla nimi ja faili nimi¶

Liideses on iga faili jaoks kaks osa: hoidla nimi (storeName) ja faili nimi (fileName).

Selline jaotus tuleb blob-hoidlate eripärast. Azure Blob Storage'is ei ole päris kaustu nagu kettal – on konteinerid, mille sees on failid. Seetõttu piirdub struktuur ühe tasemega: hoidla → fail. Kohaliku ketta puhul vastab hoidla alamkaustale, näiteks wwwroot/files/contracts/, ja blob-hoidlas konteinerile.

FileStore konstandid¶

Hoidlate nimed ei ole juhuslikud stringid, mida igaüks võib omatahtsi kirjutada. Nende jaoks on eraldi staatiline klass konstantidega:

public static class FileStore
{
    public const string Contracts = "contracts";
    public const string Invoices = "invoices";
}

Kasutame koodis alati FileStore.Contracts, mitte "contracts". Nii hoiame ära kirjavead ("contract", "Contracts") ja kui hoidla nimi kunagi muutub, piisab ühe rea muutmisest. Konstantide väärtused on kompileerimise ajal fikseeritud – see on tahtlik, sest hoidlate nimed on rakenduse disaini osa, mitte seadistus.

LocalFileClient¶

Kohaliku ketta jaoks on meil LocalFileClient. See paigutab failid wwwroot/files kausta, kus iga hoidla on oma alamkaust.

using Microsoft.AspNetCore.Hosting;

public class LocalFileClient : IFileClient
{
    private readonly string _rootPath;

    public LocalFileClient(IWebHostEnvironment environment)
    {
        var webRoot = environment.WebRootPath
            ?? Path.Combine(environment.ContentRootPath, "wwwroot");

        _rootPath = Path.Combine(webRoot, "files");
    }

    public async Task SaveFileAsync(string storeName, string fileName, byte[] content)
    {
        var directory = Path.Combine(_rootPath, storeName);
        Directory.CreateDirectory(directory);

        var path = GetPath(storeName, fileName);
        await File.WriteAllBytesAsync(path, content);
    }

    public async Task<byte[]> GetFileAsync(string storeName, string fileName)
    {
        var path = GetPath(storeName, fileName);

        if (!File.Exists(path))
            return null;

        return await File.ReadAllBytesAsync(path);
    }

    public Task<bool> FileExistsAsync(string storeName, string fileName)
    {
        return Task.FromResult(File.Exists(GetPath(storeName, fileName)));
    }

    public Task DeleteFileAsync(string storeName, string fileName)
    {
        var path = GetPath(storeName, fileName);

        if (File.Exists(path))
            File.Delete(path);

        return Task.CompletedTask;
    }

    public string GetFileUrl(string storeName, string fileName)
    {
        return $"/files/{storeName}/{Path.GetFileName(fileName)}";
    }

    private string GetPath(string storeName, string fileName)
    {
        // Kliendi antud nimest võtame ainult failinime, mitte kaustateed
        var safeFileName = Path.GetFileName(fileName);
        return Path.Combine(_rootPath, storeName, safeFileName);
    }
}

Mõned olulised kohad:

  • Konstruktor võtab IWebHostEnvironment-i ja leiab wwwroot kausta. Nii ei ole tee koodi sisse kirjutatud.
  • Directory.CreateDirectory loob hoidla kausta, kui seda veel ei ole. Ilma selleta kukub esimene salvestus veaga.
  • GetPath kasutab Path.GetFileName-i, mis eemaldab failinimest kõik kaustateed. See hoiab ära failinimega ettenähtud kaustast välja pääsemise (ingl path traversal).
  • File.WriteAllBytesAsync kirjutab olemasoleva faili üle. Lepingute puhul on see soovitud: uus versioon asendab vana.
  • GetFileUrl eeldab, et wwwroot/files on staatiliste failidena kättesaadav. Selleks peab Program.cs-is olema app.UseStaticFiles().

Avalikud ja privaatsed failid

Kõik, mis on wwwroot kaustas, on veebis avalikult kättesaadav. Lepingud ja arved ei tohiks tavaliselt avalikud olla. Päris rakenduses hoitakse privaatseid faile väljaspool wwwroot-i (nt App_Data/files) ja serveeritakse autenditud kontrolleri kaudu. Siis peab ka GetFileUrl tagastama API URL-i, mitte staatilise faili URL-i.

Failide paigutus projektides¶

Meie lahenduses on failidega seotud klassid kahes projektis:

Fail Projekt Sisu
Storage/IFileClient.cs Application failioperatsioonide liides
Storage/FileStore.cs Application hoidlate nimede konstandid
Storage/LocalFileClient.cs WebApi kohaliku ketta implementatsioon
Controllers/ContractsController.cs WebApi faili vastuvõtmine
Features/Contracts/SaveContractFileCommand.cs Application command
Features/Contracts/SaveContractFileCommandHandler.cs Application handler
Features/Contracts/SaveContractFileCommandValidator.cs Application valideerija

Liides ja commandid on Application projektis, sest need ei tohi sõltuda ASP.NET Core-ist. LocalFileClient on WebApi projektis, sest ta kasutab IWebHostEnvironment-i, mis on ASP.NET Core-i tüüp.

Registreerimine¶

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddSingleton<IFileClient, LocalFileClient>();

var app = builder.Build();

app.UseStaticFiles();
app.MapControllers();

app.Run();

LocalFileClient sobib singletonina, sest ta on olekutu – hoiab ainult juurkausta teed. Kui testides tahame ketta asemel mälus olevat lahendust, piisab ainult registreerimise rea muutmisest:

builder.Services.AddSingleton<IFileClient, InMemoryFileClient>();

Ükski handler ega kontroller ei pea sellest muudatusest teadma. See ongi liidese mõte.

Failide üleslaadimine ASP.NET Core Web API-s¶

Faili saatmiseks ei kasuta HTTP päringu kehas JSON-i, sest JSON sobib hästi tekstiliste andmete jaoks, mitte binaarfailide jaoks. Selle asemel kasutatakse multipart/form-data vormingut, kus iga väli saadetakse eraldi osana koos nime, failinime ja sisuga.

ASP.NET Core pakub faili jaoks tüüpi IFormFile:

Omadus / meetod Tähendus
FileName Kliendi teatatud failinimi. Ei ole usaldusväärne – klient võib sinna kirjutada mida iganes.
ContentType Kliendi teatatud MIME-tüüp (nt application/pdf). Samuti ei ole usaldusväärne.
Length Faili suurus baitides.
CopyToAsync Kopeerib faili sisu streami.
OpenReadStream Annab faili sisu lugemiseks streami.

Kontrolleri tegevus¶

Kontroller võtab faili vastu [FromForm] atribuudiga ja loeb selle sisu baitidena:

[ApiController]
[Route("api/[controller]")]
public class ContractsController : ControllerBase
{
    [HttpPost("{id}/file")]
    [RequestSizeLimit(5 * 1024 * 1024)]
    public async Task<IActionResult> UploadFile(int id, [FromForm] IFormFile file)
    {
        // 1. Kontrollime, et fail üldse saabus
        if (file == null || file.Length == 0)
            return BadRequest("Fail on kohustuslik");

        // 2. Loeme faili sisu baitidena
        using var stream = new MemoryStream();
        await file.CopyToAsync(stream);
        var content = stream.ToArray();

        // 3. Salvestamise loogika lisame järgmises jaotises
        return Ok(new
        {
            fileName = file.FileName,
            size = content.Length
        });
    }
}

See on vaheetapp: kontrollime, et fail jõuab serverisse kohale. Faili veel ei salvestata – selle lisame järgmises jaotises commandi abil.

  • [FromForm] ütleb, et file tuleb vormiandmetest, mitte päringu keha JSON-ist. Ilma selleta ei pruugi Swagger failivalijat õigesti kuvada.
  • [RequestSizeLimit] piirab selle konkreetse endpointi päringu suurust. Suurem päring lükatakse tagasi staatusekoodiga 413 Payload Too Large.
  • MemoryStream on vajalik seetõttu, et IFormFile ei ole byte[]. Command aga võtab vastu byte[], sest Application projekt ei tohi IFormFile-i tunda.

Miks mitte saata IFormFile commandiga edasi?

IFormFile on ASP.NET Core-i tüüp. Kui command võtaks selle vastu, peaks Application projekt viitama ASP.NET Core-ile ja kogu äriloogika muutuks veebiraamistikust sõltuvaks. Seepärast teisendame faili kontrolleris byte[]-ks ja saadame commandiga edasi ainult andmed.

Proovimine Swaggeriga¶

Käivita rakendus ja ava Swagger. POST /api/contracts/{id}/file juures kuvatakse file väli failivalijana, sest parameetri tüüp on IFormFile.

  1. Vajuta Try it out.
  2. Sisesta id väärtuseks näiteks 5.
  3. Vali file välja juures PDF-fail.
  4. Vajuta Execute.

Sama päringu saab teha ka käsurealt:

curl -X POST "https://localhost:7001/api/contracts/5/file" -F "file=@leping.pdf"

Suuruse piirangud¶

Vaikimisi on päringu suurus piiratud mitmes kohas. Kui piirangut ei sea, võib klient saata gigabaidise faili ja kirjutada serveri mälu või kettaruumi täis.

Koht Vaikimisi Kuidas muuta
Kestrel (MaxRequestBodySize) 30 MB builder.WebHost.ConfigureKestrel(...)
Vormiandmete osa suurus (MultipartBodyLengthLimit) 128 MB [RequestFormLimits(MultipartBodyLengthLimit = ...)]
Üksiku endpointi piirang – [RequestSizeLimit(...)]

Näiteks kogu rakenduse jaoks 10 MB piirang:

builder.WebHost.ConfigureKestrel(options =>
{
    options.Limits.MaxRequestBodySize = 10 * 1024 * 1024;
});

Endpointi tasandil on [RequestSizeLimit(5 * 1024 * 1024)] täpsem, sest teised endpointid võivad vajada suuremat piiri.

Turvalisus¶

Failide üleslaadimine on üks levinumaid turvaaukude allikaid. Isegi kui rakendus on väike, tuleb järgida põhireegleid:

Failide üleslaadimise turvareeglid

  • Ära kasuta kliendi failinime tee jaoks. file.FileName võib olla ..\..\appsettings.json. Kasuta Path.GetFileName-i või genereeri nimi ise.
  • Kontrolli laiendit, mitte ainult ContentType-i. Kliendi teatatud MIME-tüüp on lihtsalt tekst ja seda saab vabalt valetada.
  • Piira suurust. Nii Kestrelis kui ka endpointis.
  • Ära hoia privaatseid faile wwwroot-is. Kõik seal olev on avalikult alla laaditav.
  • Päris süsteemides kontrollitakse ka faili sisu (nt PDF-i päis) ja skaneeritakse failid viirusetõrjega.

Halvasti:

// HALB: kliendi failinimi läheb otse teesse
var path = Path.Combine("wwwroot/files/contracts", file.FileName);

Kui file.FileName on ..\..\appsettings.json, kirjutatakse fail väljapoole ettenähtud kausta. Seepärast genereerime failinime serveris – seda teeme command handleris.

CQRS-i command faili salvestamiseks¶

Nüüd, kui fail on serverisse jõudnud ja teisendatud byte[]-ks, tuleb see ära salvestada. Salvestamist ei tee kontroller, vaid command handler, sest tegu on rakenduse ärilise tegevusega.

Command¶

public class SaveContractFileCommand
{
    public int ContractId { get; set; }
    public string FileName { get; set; }
    public byte[] Content { get; set; }
}

Commandis on ainult andmed, mida salvestamiseks vaja on:

  • ContractId – millise lepinguga fail seotud on.
  • FileName – kliendi antud failinimi. Sellest kasutame ainult laiendit.
  • Content – faili sisu baitidena.

Command ei sisalda faili asukohta, hoidla nime ega ühtegi muud tehnilist detaili. Need otsustab handler. Commandil ei ole ka ASP.NET Core-i tüüpe – nii saab sama commandi käivitada nii kontrollerist kui ka testist.

Handler¶

public class SaveContractFileCommandHandler
{
    private readonly IFileClient _fileClient;

    public SaveContractFileCommandHandler(IFileClient fileClient)
    {
        _fileClient = fileClient;
    }

    public async Task<Result> Handle(SaveContractFileCommand command)
    {
        var extension = Path.GetExtension(command.FileName).ToLowerInvariant();
        var fileName = $"{command.ContractId}{extension}";

        await _fileClient.SaveFileAsync(FileStore.Contracts, fileName, command.Content);

        return Result.Ok();
    }
}

Rea haaval:

  1. Laiend võetakse kliendi failinimest. Ainult laiendit on vaja – ülejäänud nime mõtleb server ise välja.
  2. Failinimi genereeritakse serveris: 5.pdf. Klient ei saa mõjutada ei kausta ega failinime, seega ei ole võimalik kaustast välja murda ega teist faili üle kirjutada.
  3. IFileClient on konstruktorist sisse antud. Handler ei tea, kas fail läheb kohalikule kettale või pilve.
  4. Hoidla nimi tuleb FileStore konstandist. Handler ütleb, mis hoidlasse fail kuulub, mitte kus see asub.
  5. Result.Ok() näitab, et tegevus õnnestus. CQRS-i reegli kohaselt command andmeid ei tagasta.

Miks sama lepingu fail kirjutatakse üle?

Kui lepingule laaditakse uus PDF, asendab see vana. See on tavaline käitumine. Kui on vaja failide ajalugu, tuleks nimeks võtta näiteks 5-20261113.pdf või Guid.NewGuid(), salvestada faili nimi andmebaasi ning vanad failid alles hoida. See muudab aga nii salvestamise kui ka allalaadimise loogikat ja jääb selle kursuse raamest välja.

Faili nime laiend ja vana fail

Kui lubada mitut laiendit (nt .pdf ja .docx), võib lepingu 5.pdf kõrvale jääda ka 5.docx, kui laiend muutub. Sellisel juhul tuleb enne salvestamist vana fail kustutada või piirduda ühe lubatud laiendiga. Meie näites lubame ainult PDF-i.

Valideerimine¶

Nagu eelmises peatükis nägime, kuuluvad commandi sisendi reeglid valideerijasse, mitte kontrollerisse:

public class SaveContractFileCommandValidator : AbstractValidator<SaveContractFileCommand>
{
    private static readonly string[] AllowedExtensions = { ".pdf" };

    public SaveContractFileCommandValidator()
    {
        RuleFor(command => command.ContractId)
            .GreaterThan(0).WithMessage("Lepingu id peab olema positiivne");

        RuleFor(command => command.FileName)
            .NotEmpty().WithMessage("Faili nimi on kohustuslik")
            .Must(HaveAllowedExtension).WithMessage("Lubatud on ainult PDF-fail");

        RuleFor(command => command.Content)
            .NotEmpty().WithMessage("Fail on tühi")
            .Must(content => content.Length <= 2 * 1024 * 1024)
            .WithMessage("Fail võib olla kuni 2 MB");
    }

    private static bool HaveAllowedExtension(string fileName)
    {
        return AllowedExtensions.Contains(Path.GetExtension(fileName).ToLowerInvariant());
    }
}

Kontrolleris piisab null- ja tühjuse kontrollist, sest [ApiController] teeb mudeli sidumise vigade puhul automaatselt 400 Bad Request. Ärireeglid – lubatud laiend ja maksimaalne suurus – on valideerijas.

Laiend ei tõesta faili tüüpi

Ka .pdf laiendiga fail võib olla hoopis midagi muud. Tõsisemates süsteemides kontrollitakse faili algusbaite (nn magic bytes) või teisendatakse pilt enne salvestamist uuesti. Meie kursuses piirdume laiendi ja suurusega.

Valideerija registreeritakse eelmises peatükis näidatud viisil:

builder.Services.AddValidatorsFromAssemblyContaining<SaveContractFileCommandValidator>();

Kontrolleri lõplik versioon¶

Nüüd saab kontrolleri vaheetapi asendada päris lahendusega, mis saadab commandi dispatcherile:

[ApiController]
[Route("api/[controller]")]
public class ContractsController : ControllerBase
{
    private readonly Dispatcher _dispatcher;

    public ContractsController(Dispatcher dispatcher)
    {
        _dispatcher = dispatcher;
    }

    [HttpPost("{id}/file")]
    [RequestSizeLimit(5 * 1024 * 1024)]
    public async Task<IActionResult> UploadFile(int id, [FromForm] IFormFile file)
    {
        if (file == null || file.Length == 0)
            return BadRequest("Fail on kohustuslik");

        using var stream = new MemoryStream();
        await file.CopyToAsync(stream);

        var command = new SaveContractFileCommand
        {
            ContractId = id,
            FileName = file.FileName,
            Content = stream.ToArray()
        };

        await _dispatcher.SendAsync(command);

        return StatusCode(StatusCodes.Status201Created);
    }
}

Kontrolleri vastutus on nüüd selgelt piiratud:

  • võtta HTTP päring vastu,
  • kontrollida, et fail on olemas,
  • teisendada IFormFile commandi andmeteks,
  • saata command dispatcherile,
  • tagastada sobiv staatusekood.

Kontroller ei tea, kuhu fail salvestatakse ega kuidas seda tehakse.

Dispatcheri meetodi nimi

Selles materjalis on dispatcheri meetodi nimeks SendAsync. Kui sinu projektis on meetodi nimi teine (nt DispatchAsync), kasuta seda, mis projektis olemas on – tähtis on, et kontroller ei kutsuks handlerit otse.

    K->>C: POST /api/contracts/5/file (multipart/form-data)
    C->>C: IFormFile → byte[]

Kokkuvõte¶

  • Failioperatsioonid ei kuulu kontrollerisse – need tuleb peita liidese taha, et rakendus ei sõltuks konkreetsest hoidlast.
  • IFileClient kirjeldab salvestamise, lugemise, olemasolu kontrolli, kustutamise ja URL-i genereerimise.
  • Hoidla nimi ja faili nimi hoiavad liidese lihtsana ning töötavad nii kohaliku ketta kui ka blob-hoidlatega.
  • FileStore hoiab hoidlate nimed ühes kohas ja väldib kirjavigu.
  • LocalFileClient salvestab failid wwwroot/files/<hoidla>/ kausta; päris projektis tuleb privaatsed failid hoida väljaspool wwwroot-i.
  • IFormFile võtab faili vastu multipart/form-data päringust; kontroller teisendab selle byte[]-ks, sest Application projekt ei tohi ASP.NET Core-i tüüpe tunda.
  • Suurust ja laiendit tuleb piirata ning kliendi failinime mitte kunagi otse teena kasutada.
  • Command sisaldab ainult andmeid, handler genereerib turvalise failinime ja kutsub IFileClient-i, valideerija kontrollib ärireegleid.
  • Hoidla vahetamine käib ainult Program.cs-is tehtava registreerimise kaudu.

Harjutused¶

  1. Kirjuta SaveInvoiceFileCommand ja SaveInvoiceFileCommandHandler, mis salvestab arve PDF-i hoidlasse FileStore.Invoices. Kasuta failinimena arve id-d ja laiendit. Testi Swaggeriga.
  2. Lisa eelmisele ülesandele SaveInvoiceFileCommandValidator, mis lubab ainult PDF-faile suurusega kuni 1 MB. Kontrolli, et liiga suur fail annab 400 Bad Request.
  3. Loo InMemoryFileClient, mis hoiab faile Dictionary<string, byte[]>-s. Registreeri see testkeskkonnas LocalFileClient-i asemel ja veendu, et handleri koodi ei pea muutma.
  4. Loo endpoint GET /api/contracts/{id}/file, mis tagastab IFileClient.GetFileAsync abil lepingu PDF-i. Kui faili ei ole, tagasta 404 Not Found.
  5. (Raske) Loe LocalFileClient-i juurkaust konfiguratsioonist (nt appsettings.json väärtusest FileStorage:RootPath). Kirjuta test, mis kontrollib, et failinimi ..\..\appsettings.json ei pääse juurkaustast välja.
