Tarkvara arhitektuur¶

Tarkvara arhitektuur on plaan, kuidas programm üles ehitatakse. See on nagu maja plaan – enne kui hakkad ehitama, pead teadma, kuhu tulevad toad, uksed ja aknad.

Miks arhitektuur on tähtis?¶

  • Arusaadavus – kui kood on loogiliselt jaotatud, on uutel arendajatel lihtne sisse elada
  • Muudetavus – kui ühte osa on vaja muuta, ei lähe teised osad katki
  • Testitavus – hästi jaotatud koodi on lihtsam testida
  • Taaskasutatavus – samu komponente saab kasutada mitmes kohas
  • Mastaabitavus – kui kasutajaid tuleb juurde, saab süsteemi lihtsamini võimsamaks muuta

Mis juhtub, kui arhitektuurile tähelepanu ei pööra?¶

  • "Spagetikood" – kõik on kõigega seotud, keegi ei saa aru, mis toimub
  • Ühe vea parandamine tekitab kolm uut – sest koodil pole selgeid piire
  • Uue funktsionaalsuse lisamine on aeglane ja valus – isegi väike muudatus nõuab suurt ümberkirjutamist
  • Testimine on võimatu – kood on nii sassis, et ühikteste ei saa kirjutada
  • Keegi ei taha sellise projektiga töötada – kogenud arendajad põgenevad

Tuntumad arhitektuurimudelid¶

Monoliitne arhitektuur¶

Kogu rakendus on üks tervik – kõik funktsioonid on samas projektis ja sama koodibaasi sees.

graph TD
    subgraph "Monoliitne rakendus"
        UI["Kasutajaliides (UI)"] --> Logika["Ärilogika"] --> Andmed["Andmed"]
    end

Sobib: väikestele projektidele, prototüüpidele, õppetööks Ei sobi: suurtele süsteemidele, mitme meeskonnaga projektidele

Näide: lihtne konsoolirakendus, ASP.NET veebileht, kus kõik on ühes projektis

Kihiline (layered) arhitektuur¶

Rakendus on jaotatud kihtidesse. Iga kiht tegeleb ainult oma asjaga.

graph TD
    Esitlus["Esitluskiht (kasutajaliides)"] --> Aari["Ärilogika kiht (reeglid ja arvutused)"]
    Aari --> Andmed["Andmekiht (andmebaas)"]

Reegel: iga kiht suhtleb ainult temast allpool oleva kihiga.

Näide: ASP.NET MVC rakendus – Controller (esitlus), Service (ärilogika), Repository (andmed)

MVC (Model-View-Controller)¶

Veebirakenduste levinuim mudel. Kolm osa:

  • Model – andmed ja ärilogika
  • View – HTML leht, mida kasutaja näeb
  • Controller – vahendaja, võtab kasutaja päringu vastu ja otsustab, mida teha
graph LR
    Paring["Päring"] --> Controller["Controller"]
    Controller --> Model["Model"]
    Model --> View["View"]
    View --> Vastus["Vastus kasutajale"]

Näide: ASP.NET Core MVC, Ruby on Rails, Laravel

REST API arhitektuur¶

Rakendus on jaotatud kaheks: klient (frontend) ja server (backend). Nad suhtlevad HTTP päringute kaudu.

graph TD
    Brauser["Brauser (JS/React/Angular)"] -->|HTTP päring| API["REST API (ASP.NET Core)"]
    API -->|SQL päring| DB[("Andmebaas")]

Põhimõtted: - Igal ressursil on oma URL (/api/raamatud, /api/opilased) - Kasutatakse HTTP meetodeid: GET (loe), POST (loo), PUT (uuenda), DELETE (kustuta) - Server ei hoia meeles, kes on sisse logitud – iga päring on iseseisev

Näide: ASP.NET Core Web API + React/Blazor frontend

CQRS (Command Query Responsibility Segregation)¶

CQRS jagab lugemise ja kirjutamise eraldi:

  • Command – muudab andmeid (lisa, uuenda, kustuta). Ei tagasta andmeid.
  • Query – loeb andmeid. Ei muuda midagi.
graph LR
    Command["Command (kirjutab)"] --> DB1[("Andmebaas")]
    Query["Query (loeb)"] --> DB2[("Andmebaas")]

Miks kasulik? - Lugemine ja kirjutamine võivad olla eraldi optimeeritud - Loetav kood – näed kohe, kas tegu on käsuga või päringuga - Sobib hästi API-de ja keerukama ärilogikaga süsteemidele

Näide: ASP.NET Core Web API, kus igal tegevusel on oma klass – LisaRaamatCommand, HangiRaamatudQuery

Mikroteenused (Microservices)¶

Rakendus on jaotatud väikesteks sõltumatuteks teenusteks. Iga teenus vastutab ühe kindla funktsiooni eest.

graph TD
    subgraph "Teenused"
        Kasutaja["Kasutaja teenus"]
        Tellimus["Tellimus teenus"]
        Makse["Makse teenus"]
    end
    Kasutaja --> Gateway["API Gateway"]
    Tellimus --> Gateway
    Makse --> Gateway
    Gateway --> Klient["Kasutaja"]

Eelised: iga teenust saab arendada ja paigaldada eraldi, erinevad meeskonnad saavad töötada eri teenustel Puudused: keerukas hallata, vajab palju infrat (Docker, Kubernetes)
