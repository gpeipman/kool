Valideerimine¶

Valideerimine tähendab andmete kontrollimist reeglite vastu enne, kui rakendus nendega midagi teeb. Kui valideerimist ei ole, jõuavad andmebaasi tühjad pealkirjad, negatiivsed lehekülgede arvud või aastad, mis on tulevikus. Selliste andmetega hakkab rakendus hiljem käituma ettearvamatult ja vigade põhjust leida on raske.

Meie projektis on valideerimine seni olnud ainult ühes kohas: Data kausta entiteetide küljes on DataAnnotations atribuudid. Features kausta commandid ja queryd on aga eraldi klassid, millel valideerimist ei ole, ja neid me ka ei testi. Selles peatükis vaatame, miks sellest ei piisa, kuidas commande ja query-sid FluentValidationi abil valideerida ning kuidas valideerimist testida.

Miks valideerimine on vajalik?¶

  • Andmete kvaliteet – andmebaasi jõuab ainult see, mis vastab reeglitele.
  • Arusaadavad veateated – klient saab teada, milline väli on vale, mitte lihtsalt "500 Internal Server Error".
  • Turvalisus – liiga pikad või ootamatud väärtused võivad põhjustada erindeid ja liigset koormust.
  • Ärireeglid – osa reegleid ei ole andmebaasi tasandil üldse võimalik kirjeldada (nt "ilmumisaasta ei tohi olla tulevikus").
  • Vähem vigu – vigane sisend peatatakse enne, kui jõutakse andmebaasi päringute ja salvestusteni.

Valideerimine kliendis ja serveris¶

Kus Mida annab Kas usaldada?
Klient (brauser, mobiilirakendus) Kiire tagasiside, kasutajat ei sunnita vormi uuesti täitma Ei – kliendi saab alati vahele jätta (Postman, curl)
Server Tõeline kaitse, kõik päringud läbivad selle Jah – see on ainus usaldusväärne koht

Klient ei ole kunagi usaldusväärne. Postmaniga saab saata täpselt sellise JSON-i, nagu ise tahad, seega peavad kõik reeglid kehtima ka serveris.

DataAnnotations atribuudid entiteetidel¶

Data kausta klassid on meil kaetud System.ComponentModel.DataAnnotations atribuutidega:

public class Book
{
    public int Id { get; set; }

    [Required(ErrorMessage = "Pealkiri on kohustuslik")]
    [MaxLength(200)]
    public string Title { get; set; }

    [Required(ErrorMessage = "Autor on kohustuslik")]
    [MaxLength(100)]
    public string Author { get; set; }

    [MaxLength(20)]
    public string Isbn { get; set; }

    [Range(1, 10000)]
    public int Pages { get; set; }

    [Range(1450, 2100)]
    public int YearPublished { get; set; }

    public bool IsAvailable { get; set; }
}

Levinumad atribuudid:

Atribuut Mida kontrollib Näide
[Required] Väli peab olema olemas ja tühi string ei ole lubatud [Required] public string Title { get; set; }
[MaxLength] / [MinLength] Stringi või massiivi pikkus [MaxLength(200)]
[StringLength] Stringi pikkus koos miinimumiga [StringLength(200, MinimumLength = 3)]
[Range] Arv või kuupäev vahemikus [Range(1, 10000)]
[RegularExpression] Väärtus vastab mustrile [RegularExpression(@"^\d{13}$")]
[EmailAddress] E-posti aadressi formaat [EmailAddress]
[Compare] Kahe välja väärtused on samad [Compare(nameof(Password))]

Entity atribuutidel on meie projektis kaks rolli:

  1. EF Core loeb neid andmebaasi skeemi loomisel – [Required] teeb veeru NOT NULL-iks, [MaxLength(200)] teeb nvarchar(200).
  2. Mudeli sidumine (model binding) kontrollib neid siis, kui entiteet ise on kontrolleri meetodi parameetriks.

Entity atribuudid ei valideeri commandi

Kui kontroller võtab vastu SaveBookCommand ja entiteet Book luuakse alles handleris, ei puutu entity atribuudid sisendandmetega üldse kokku. Kontroll toimub andmebaasi tasandil alles SaveChangesAsync() hetkel – ja siis tekib DbUpdateException, mille tulemuseks on kliendile 500, mitte arusaadav 400.

Praegune olukord projektis¶

graph LR
    K["Klient (Postman)"] --> C["BooksController"]
    C --> D["Dispatcher"]
    D --> H["SaveBookCommandHandler"]
    H --> B["new Book()"]
    B --> DB[("Andmebaas")]

Command liigub kontrollerist läbi dispatcheri handlerini ning entiteet luuakse alles handleris. Seega:

  • commandi välju ei kontrolli keegi,
  • entiteedi atribuudid rakenduvad alles andmebaasi tasandil,
  • viga jõuab kliendini hilja ja arusaamatult.

Miks valideerida commande ja query-sid?¶

Commandid¶

Command on rakenduse piir – ainus koht, kuhu kliendi andmed sisenevad. Entiteet luuakse alles handleris, seega peab kogu sisendi kontroll toimuma commandi peal.

  • Varajane peatumine – vigane command peatatakse enne andmebaasi päringut ja salvestust.
  • Õige veakood – klient saab 400 Bad Request koos väljapõhiste teadetega, mitte 500.
  • Ärireeglid, mida andmebaas ei tea – nt aasta ei tohi olla tulevikus, ISBN peab olema unikaalne.
  • Üks koht – sama commandi valideeritakse alati ühtemoodi, olenemata sellest, kas seda kutsutakse kontrollerist või testist.

Queryd¶

Ka päringu sisend võib olla vale ja see võib põhjustada vigu või liigset koormust:

  • Id peab olema positiivne – FindAsync(-1) on mõttetu andmebaasipäring.
  • Leheküljenumber ja lehekülje suurus peavad olema mõistlikus vahemikus. PageSize = 100000 võib tuua mällu kogu tabeli.
  • Mõnikord on päringu mõttekus andmebaasist sõltuv – nt küsitud lehekülge ei pruugi üldse olemas olla.

Query ei muuda andmeid, kuid vale query sisend viib ikkagi erindini või ebaotstarbeka tööni. Seepärast valideerime ka query-sid.

Miks valideerimist testida?¶

Praegu me commande ja query-sid ei testi. See tähendab, et iga valideerimisreegli õigsust kontrollime käsitsi Postmaniga – aeglaselt, juhuslikult ja iga muudatuse järel uuesti. Valideerimise testid annavad selle töö automaatselt ära:

  • Regressioonide kaitse – kui keegi hiljem MaximumLength(200) väärtuseks 500 paneb, kukub test kohe läbi.
  • Test on spetsifikatsioon – testide nimedest on näha, millised reeglid kehtivad. Uus inimene projektis loeb testid läbi ja saab aru, mida süsteem lubab ja mida mitte.
  • Piirväärtused on kõige veaohtlikumad – 0, -1, täpselt lubatud maksimum, maksimum + 1. Neid on käsitsi tüütu proovida, testiga käivad need sekunditega.
  • Kiire tagasiside – valideerimine on puhas loogika, enamik testidest jookseb ilma andmebaasi ja veebiserverita.
  • Handleri käitumine – test kinnitab, et vigase commandi korral ei tehta andmebaasi päringut ega salvestust.
  • Andmebaasist sõltuvad reeglid – unikaalsuse kontrolli saab testida mälusisese andmebaasiga, ilma päris SQL Serverita.

FluentValidation¶

FluentValidation on .NET-i teek, kus valideerimisreeglid kirjutatakse eraldi valideerija klassi loetava koodina. Erinevalt atribuutidest saab reegleid kirjutada kahel väljal põhinevaid (nt algus enne lõppu), tingimuslikke ja andmebaasi pöörduvaid kontrolle.

Atribuutidega võrreldes:

DataAnnotations FluentValidation
Kus reeglid asuvad Mudeli/entiteedi küljes Eraldi valideerija klassis
Keerukad reeglid Raskesti väljendatavad Lihtsad (Must, When, MustAsync)
Andmebaasi pöördumine Ei ole ette nähtud Jah (MustAsync)
Testimine Võimalik, kuid kohmakas Väga lihtne (TestValidate)
Kasutuskoht Mudeli sidumine Commandid, queryd, äriloogika

Paigaldamine¶

dotnet add package FluentValidation
dotnet add package FluentValidation.DependencyInjectionExtensions

Commandi valideerija¶

Alustame lihtsamate reeglitega, mis kontrollivad ainult commandi välju:

using FluentValidation;

public class SaveBookCommandValidator : AbstractValidator<SaveBookCommand>
{
    public SaveBookCommandValidator()
    {
        RuleFor(command => command.Title)
            .NotEmpty().WithMessage("Pealkiri on kohustuslik")
            .MaximumLength(200).WithMessage("Pealkiri võib olla kuni 200 tähemärki");

        RuleFor(command => command.Author)
            .NotEmpty().WithMessage("Autor on kohustuslik")
            .MaximumLength(100).WithMessage("Autori nimi võib olla kuni 100 tähemärki");

        RuleFor(command => command.Pages)
            .InclusiveBetween(1, 10000)
            .WithMessage("Lehekülgede arv peab olema 1 kuni 10000");

        RuleFor(command => command.YearPublished)
            .InclusiveBetween(1450, DateTime.Now.Year)
            .WithMessage($"Ilmumisaasta peab olema 1450 kuni {DateTime.Now.Year}");
    }
}

Levinumad reeglid:

Reegel Mida kontrollib
NotEmpty() Väli ei ole tühi ega koosne ainult tühikutest
NotNull() Väärtus ei ole null
Length(min, max) Stringi pikkus vahemikus
MaximumLength(max) / MinimumLength(min) Stringi maksimum- või miinimumpikkus
InclusiveBetween(min, max) Arv on vahemikus, otsad kaasa arvatud
GreaterThan(0) Arv on suurem kui antud väärtus
EmailAddress() E-posti aadressi formaat
Matches(regex) Väärtus vastab regulaaravaldisele
Must(...) / MustAsync(...) Oma kontroll, sh andmebaasi päring
When(...) Reegel kehtib ainult teatud tingimusel

Reegel, mis pöördub andmebaasi¶

Osa reegleid ei saa kontrollida ainult commandi väljade põhjal – näiteks ISBN peab olema unikaalne. Sellisel juhul sõltub valideerija DbContext-ist ja kasutame MustAsync-i. Täiendame eelmist valideerijat:

using FluentValidation;
using Microsoft.EntityFrameworkCore;

public class SaveBookCommandValidator : AbstractValidator<SaveBookCommand>
{
    private readonly LibraryContext _dbContext;

    public SaveBookCommandValidator(LibraryContext dbContext)
    {
        _dbContext = dbContext;

        RuleFor(command => command.Title)
            .NotEmpty().WithMessage("Pealkiri on kohustuslik")
            .MaximumLength(200).WithMessage("Pealkiri võib olla kuni 200 tähemärki");

        RuleFor(command => command.Author)
            .NotEmpty().WithMessage("Autor on kohustuslik")
            .MaximumLength(100).WithMessage("Autori nimi võib olla kuni 100 tähemärki");

        RuleFor(command => command.Pages)
            .InclusiveBetween(1, 10000)
            .WithMessage("Lehekülgede arv peab olema 1 kuni 10000");

        RuleFor(command => command.YearPublished)
            .InclusiveBetween(1450, DateTime.Now.Year)
            .WithMessage($"Ilmumisaasta peab olema 1450 kuni {DateTime.Now.Year}");

        RuleFor(command => command.Isbn)
            .Cascade(CascadeMode.Stop)
            .NotEmpty().WithMessage("ISBN on kohustuslik")
            .MustAsync(BeUniqueIsbn).WithMessage("Selle ISBN-iga raamat on juba olemas");
    }

    private async Task<bool> BeUniqueIsbn(string isbn, CancellationToken cancellationToken)
    {
        return !await _dbContext.Books
            .AnyAsync(book => book.Isbn == isbn, cancellationToken);
    }
}

Pane tähele Cascade(CascadeMode.Stop): kui ISBN on tühi, ei minda andmebaasi pärima. Ilma selleta tehtaks tühja ISBN-iga ikkagi üks mõttetu SELECT päring. Andmebaasi pöörduvate reeglite puhul tasub alati mõelda, kas päringut saab vältida.

Unikaalsus ja andmebaas

AnyAsync kontroll ei taga unikaalsust 100% – kahe samaaegse päringu korral võivad mõlemad kontrolli läbida. Tõeline garantii on andmebaasis UNIQUE indeks. Valideerimine annab siiski kliendile kiire ja arusaadava veateate; indeks on viimane kaitse.

Query valideerija¶

using FluentValidation;
using Microsoft.EntityFrameworkCore;

public class ListBooksQueryValidator : AbstractValidator<ListBooksQuery>
{
    private readonly LibraryContext _dbContext;

    public ListBooksQueryValidator(LibraryContext dbContext)
    {
        _dbContext = dbContext;

        RuleFor(query => query.Page)
            .GreaterThan(0).WithMessage("Lehekülje number peab olema vähemalt 1");

        RuleFor(query => query.PageSize)
            .InclusiveBetween(1, 100)
            .WithMessage("Lehekülje suurus peab olema 1 kuni 100");

        RuleFor(query => query.Page)
            .MustAsync(PageExists).WithMessage("Sellist lehekülge ei ole olemas")
            .When(query => query.PageSize > 0);
    }

    private async Task<bool> PageExists(ListBooksQuery query, int page, CancellationToken cancellationToken)
    {
        var rowCount = await _dbContext.Books.CountAsync(cancellationToken);
        var pageCount = (int)Math.Ceiling((double)rowCount / query.PageSize);

        return pageCount == 0 || page <= pageCount;
    }
}

Siin sõltub reegel kahest väljast (Page ja PageSize) ja andmebaasi ridade arvust. Just selliseid reegleid on DataAnnotations atribuutidega võimatu kirjeldada. When-tingimus hoiab ära nulliga jagamise, kui PageSize ise on vale.

Registreerimine¶

Valideerijad tuleb DI-konteinerisse registreerida. Kõige lihtsam on lasta FluentValidationil leida kõik valideerijad ühest assembly-st:

using FluentValidation;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<LibraryContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("DefaultConnection")));

builder.Services.AddValidatorsFromAssemblyContaining<SaveBookCommandValidator>();

AddValidatorsFromAssemblyContaining registreerib valideerijad scoped elueaga. See on oluline, sest valideerija kasutab DbContext-i, mis on samuti scoped.

Kokkuvõte¶

  • Valideerimine kontrollib andmeid enne, kui rakendus nendega midagi teeb; serveripoolne valideerimine on ainus usaldusväärne.
  • DataAnnotations entiteedil kirjeldavad andmebaasi skeemi, kuid ei valideeri commande – entiteet luuakse alles handleris.
  • Commandid ja queryd on rakenduse piir, seega peab nende sisend olema valideeritud.
  • FluentValidation kirjutab reeglid eraldi valideerija klassi; MustAsync-iga saab kaasata ka andmebaasipäringu (nt ISBN unikaalsus).
  • Andmebaasist sõltuvaid reegleid testitakse InMemory andmebaasiga, päris andmebaasi pole testide jaoks vaja.
