Git ja GitHub¶

Lähtekoodihoidla (ingl repository või repo) on koht, kus hoitakse kogu projekti lähtekoodi ja selle muudatuste ajalugu. See lahendab mitu olulist probleemi: saad alati vaadata, kes mida muutis ja millal; vajadusel minna tagasi vana versiooni juurde; teha erinevaid asju paralleelselt (harud); ja teha koostööd teiste arendajatega ilma, et keegi teise tööd kogemata üle kirjutaks.

Lähtekoodihoidlate ajalugu¶

Ajastu Tüüp Süsteem(id) Tugevus
1980–1990 Kohalik RCS Üksikarendaja versioonihaldus
1990–2000 Keskne CVS Mitme arendaja koostöö, üks tõeallikas
2000–2010 Keskne SVN Metaandmed, aatomilised tehingud, töökindlus
2005–... Hajutatud Git, Mercurial Igal arendajal terve koopia, kiire, võimas harude haldus

Git on tänapäeva standard, mida toetavad GitHub, GitLab, Azure DevOps ja Bitbucket.

Mis on Git?¶

Git on süsteem, mis aitab sul oma koodi ajalugu hallata. Iga kord, kui teed olulise muudatuse, salvestad selle "commit'ina" – nagu mängus salvestuspunkt. Alati saad vaadata, mis enne oli, ja vajadusel vana versiooni juurde tagasi minna.

Kogu projekti ajalugu on sinu enda arvutis. Sa ei vaja internetiühendust, et commitsid teha, harusid luua või ajalugu sirvida. Alles siis, kui tahad oma tööd teistega jagada, läheb vaja veebi.

Harud (branches) on Giti üks võimsamaid omadusi. Saad teha uue haru, katsetada seal julgelt uusi asju ja kui kõik töötab, ühendada haru tagasi põhiharuga. Kui katse ebaõnnestub, kustutad haru lihtsalt ära – põhikood jääb puutumata.

Kõik commits on kinnitatud turvalise räsiga. Keegi ei saa hiljem ajalugu salaja muuta – kui midagi on committitud, on see igavesti alles.

Mis on GitHub?¶

Kui Git on tööriist sinu arvutis, siis GitHub on veebikeskkond, kus saad oma Giti hoidlaid teistega jagada ja koostööd teha. GitHub on nagu sotsiaalvõrgustik programmeerijatele – ainult et piltide asemel jagatakse koodi.

GitHubi kaudu saad: - oma koodi pilve üles laadida ja sealt teistele kättesaadavaks teha - teha pull request'e – enne kui su muudatused põhikoodi jõuavad, saavad kaaslased neid üle vaadata ja parandusi soovitada - hallata vigu ja uusi ideid issue'dega - seada sisse automaatseid töövooge (GitHub Actions) – näiteks iga commit'i peale jooksutada testid ja kontrollida, et kood töötab

GitHub on tänapäeval populaarseim platvorm, kuid olemas on ka teisi: GitLab, Bitbucket ja Azure DevOps. Kõik nad teevad sisuliselt sama asja – aitavad Giti abil koos programmeerida.

Giti töövood¶

Kuidas Giti igapäevaselt kasutada, sõltub tiimi suurusest ja projekti iseloomust. Vaatame kahte levinumat töövoogu.

Master-only töövoog¶

Lihtsaim viis – kõik arendajad teevad commitsid otse master (või main) harusse. Igaüks tõmbab enne alustamist viimase versiooni alla ja lükkab oma muudatused pärast üles. See toimib hästi väikestes tiimides või üksi töötades, kus muudatusi tuleb vähe ja keegi teise tööd kogemata üle ei kirjuta.

%%{init: { "theme": "base", "gitGraph": { "mainBranchName": "master" } } }%%
gitGraph
   commit
   commit
   commit
   commit
   commit

Puuduseks on risk: kui keegi lükkab üles katkise koodi, on see kohe kõigil ees. Samuti pole koodi ülevaatamise protsessi – muudatused jõuavad otse tootlikku harusse ilma kontrollita.

Feature branch + pull request töövoog¶

Suuremates tiimides kasutatakse harude süsteemi. Iga uus funktsionaalsus saab oma haru, mis hargneb master harust ja nimetatakse kirjeldavalt (nt feature/login või fix/typo). Arendaja teeb kõik oma muudatused selles harus ja kui töö valmis, avab GitHubis pull request'i.

%%{init: { "theme": "base", "gitGraph": { "mainBranchName": "master" } } }%%
gitGraph
   commit
   commit
   branch feature/120-login
   checkout feature/120-login
   commit
   commit
   commit
   checkout master
   merge feature/120-login
   commit

Pull request on palve oma muudatused põhiharuga ühendada. Enne ühendamist saavad teised arendajad koodi üle vaadata, kommentaare jätta ja parandusi nõuda. Kui kõik on rahul, ühendatakse haru master harusse ja feature haru kustutatakse.

See töövoog hoiab põhiharu koodi korras ja vigadest puhtana. Katkine kood satub harru, mitte põhiharru. Lisaks õpivad kõik teiste koodist ja tekib loomulik kvaliteedikontroll.

Põhilised Giti käsud¶

Käsk Mida teeb
git init Loob praegusesse kausta uue Giti hoidla
git clone <aadress> Kopeerib olemasoleva hoidla enda arvutisse
git status Näitab, millised failid on muudetud ja mis harus oled
git add <fail> Lisab faili järgmisse commit'i (staging)
git commit -m "sõnum" Salvestab muudatused koos kirjeldusega
git log Näitab commit'ide ajalugu
git diff Näitab täpselt, mis on failides muutunud
git branch <nimi> Loob uue haru
git checkout <nimi> Liigub teise haru või vana commit'i juurde
git switch <nimi> Tänapäevasem viis haru vahetamiseks
git merge <nimi> Ühendab teise haru praegusesse harusse
git pull Laeb alla viimase versiooni ja ühendab selle
git push Lükkab oma commitsid üles kaugserverisse
git fetch Laeb alla uusimad muudatused ilma neid ühendamata

Pull request¶

Pull request (lühendatult PR) on GitHubi tööriist, millega palud oma haru muudatused põhiharuga ühendada. See on justkui "Hei, vaadake üle, mis ma tegin!" hüüatus oma tiimile.

Miks seda vaja on?¶

Pull request hoiab koodi kvaliteeti kõrgel. Enne kui midagi masteri jõuab, saavad teised arendajad: - koodi üle vaadata ja vigadele osutada - kommentaare ja ettepanekuid jätta - muudatusi välja nõuda, kui midagi on puudu või valesti

See on justkui teine paar silmi – tihti märkab teine inimene sinu koodis asju, mida sa ise enam ei näe, sest oled sellega liiga ära harjunud.

Kuidas see käib?¶

  1. Lükka oma feature haru GitHubi üles (git push)
  2. Ava GitHubis pull request feature harust master harru
  3. Kirjuta pealkiri ja kirjeldus – mida sa muutsid ja miks
  4. Kaaslased vaatavad üle, kommenteerivad ja kiidavad heaks
  5. Kui kõik on rahul, ühendatakse PR ja feature haru kustutatakse

Pull request pole mõeldud ainult suurte muudatuste jaoks. Ka väikeste paranduste puhul on hea teha PR – see harjutab tiimitööd ja hoiab koodi korras.

Merge conflict¶

Merge conflict (ühendamistüli) tekib siis, kui Git ei suuda automaatselt otsustada, milline koodijupp peaks jääma. See juhtub siis, kui kaks arendajat on muutnud sama faili samu ridu ja nende muudatused lähevad omavahel vastuollu.

Kuidas see tekib?¶

Oletame, et sina ja su kaaslane muudate mõlemad Program.cs faili sama meetodi sisu. Sina teed seda feature/login harus, kaaslane aga feature/email harus. Kui esimene haru ühendatakse masteri ja siis proovitakse teist ühendada, ei tea Git kumma versiooni jätta – sinu oma või kaaslase oma. Tulemuseks on merge conflict.

Kuidas seda lahendada?¶

Kui Git teatab merge conflict'ist, näevad konfliktsed kohad failis välja umbes nii:

<<<<<<< feature/login
Console.WriteLine("Sisselogimine õnnestus");
=======
Console.WriteLine("E-kiri saadetud");
>>>>>>> feature/email

<<<<<<< ja ======= vahel on sinu muudatused, ======= ja >>>>>>> vahel on teise haru muudatused. Lahendus on lihtne: mine faili sisse, kustuta konfliktimarkerid (<<<<<<<, =======, >>>>>>>) ja jäta alles see kood, mis peaks jääma – üks versioon, mõlemad koos või hoopis midagi kolmandat.

Pärast parandust ütled Gitile, et konflikt on lahendatud: - git add <fail> – märgid faili lahendatuks - git commit – lõpetad merge'i uue commit'iga

Mida edasi teha?¶

Merge conflict on normaalne osa tiimitööst. Mida tihedamini oma haru master haruga ühendad (git merge master), seda väiksem on tõenäosus, et hiljem tekib suur ja keeruline konflikt. Kui tundub, et konflikt läheb keeruliseks, küsi teiselt arendajalt abi – tema teab kõige paremini, miks ta seda koodi muutis.
